## 1. Загальна характеристика проєкту та бази даних

Проєкт **Crypto Pulse** є інформаційною системою для роботи з криптовалютними даними. У системі користувач може зареєструватися, мати власний профіль, додавати монети до списку обраних, створювати цінові сповіщення, а також переглядати результати роботи ML-моделі, яка формує торгові сигнали.

Для зберігання даних у проєкті використовується реляційна база даних **PostgreSQL** у середовищі **Supabase**. Supabase було обрано тому, що це хмарна платформа, яка надає готову PostgreSQL-базу, засоби автентифікації користувачів, керування доступом і зручний веб-інтерфейс для роботи з таблицями. Завдяки розміщенню БД у спільному хмарному середовищі всі учасники команди та всі частини застосунку працюють з одними й тими самими актуальними даними, а не з різними локальними копіями. Це спрощує спільну розробку, тестування та підтримку проєкту. Крім того, Supabase поєднує PostgreSQL із системою авторизації та механізмом `Row-Level Security`, тому в проєкті можна не лише зберігати дані, а й обмежувати доступ користувачів до власних записів. У Supabase окремо існує системна таблиця `auth.users`, яка відповідає за автентифікацію користувачів. Для прикладних даних проєкту використовується власна схема `public`.

Основні таблиці бази даних:

1. `auth.users` - системні облікові записи користувачів Supabase.
2. `public.users` - профілі користувачів застосунку.
3. `public.user_favorites` - криптовалюти, які користувач додав до обраного.
4. `public.alerts` - персональні сповіщення про досягнення певної ціни.
5. `public.ml_models` - натреновані ML-моделі для різних криптовалют і таймфреймів.
6. `public.model_predictions` - історія прогнозів, які сформувала ML-модель.

Основні зв'язки між таблицями:

- `public.users.id` пов'язаний із `auth.users.id`;
- `public.user_favorites.user_id` посилається на `auth.users.id`;
- `public.alerts.user_id` посилається на `auth.users.id`.

## 4. Лабораторна робота №1. Створення схеми БД

### 4.1. Що саме з ЛР 1 використано у проєкті

У межах першої лабораторної роботи потрібно побудувати схему бази даних, визначити таблиці, поля, типи даних, ключі та обмеження цілісності. У проєкті **Crypto Pulse** це реалізовано повноцінно через SQL-схему бази даних.

У проєкті використано:

- кілька взаємопов'язаних таблиць;
- первинні ключі;
- зовнішні ключі;
- сурогатні ключі;
- унікальні обмеження;
- обмеження `NOT NULL`;
- значення за замовчуванням `DEFAULT`;
- індекси для швидкого пошуку;
- каскадне видалення пов'язаних записів.

### 4.2. Які таблиці створені і для чого вони потрібні

#### Таблиця `public.users`

Таблиця `users` зберігає додаткову інформацію про користувача, якої немає в системній таблиці Supabase Auth: ім'я, прізвище, username, телефон, регіон, аватар, тарифний план, Telegram-дані та службові дати.

```sql
CREATE TABLE IF NOT EXISTS public.users (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email TEXT NOT NULL UNIQUE,
  is_active BOOLEAN NOT NULL DEFAULT true,
  username VARCHAR(100),
  first_name VARCHAR(100),
  last_name VARCHAR(100),
  ...
);
```

Оператор `CREATE TABLE` створює нову таблицю `public.users`, якщо вона ще не існує. У ній додаються поля для ідентифікатора користувача, email, стану акаунта та основних персональних даних. Уже на етапі створення таблиці одразу задаються ключові обмеження: первинний ключ, зв'язок із `auth.users`, унікальність email та значення за замовчуванням для поля активності.

Тут:

- `id` є первинним ключем;
- той самий `id` одночасно є зовнішнім ключем на `auth.users(id)`;
- `ON DELETE CASCADE` означає, що після видалення облікового запису Supabase автоматично видаляється і профіль користувача;
- поле `email` є унікальним;
- поле `is_active` має значення за замовчуванням `true`.

#### Таблиця `public.user_favorites`

Ця таблиця зберігає монети, які користувач додав до обраного.

```sql
CREATE TABLE IF NOT EXISTS public.user_favorites (
  id BIGSERIAL PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  coin_id TEXT NOT NULL,
  symbol VARCHAR(20) NOT NULL,
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT user_favorites_user_symbol_unique UNIQUE (user_id, symbol)
);
```

Через `CREATE TABLE` створюється окрема таблиця для списку обраних монет. У таблицю додаються стовпці з id запису, id користувача, технічним id монети з API, символом, назвою та датою створення запису. Окремим обмеженням `UNIQUE (user_id, symbol)` задається бізнес-правило, за яким одна й та сама монета не може двічі зберігатися в обраному одного користувача.

Важливі моменти:

- `id BIGSERIAL PRIMARY KEY` - це сурогатний ключ, який створюється автоматично через послідовність;
- `user_id` створює зв'язок "один користувач - багато обраних монет";
- `UNIQUE (user_id, symbol)` не дозволяє одному користувачу двічі додати ту саму монету.

#### Таблиця `public.alerts`

Таблиця `alerts` містить персональні умови сповіщення за ціною криптовалюти.

```sql
CREATE TABLE IF NOT EXISTS public.alerts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users(id),
  symbol TEXT NOT NULL,
  condition TEXT NOT NULL,
  target_price NUMERIC NOT NULL,
  is_active BOOLEAN DEFAULT true
);
```

У цьому блоці створюється таблиця цінових сповіщень. Через набір стовпців зберігаються користувач, символ монети, умова спрацювання, цільова ціна та ознака активності сповіщення. Поле `id` має тип `UUID` і автоматично отримує значення через `gen_random_uuid()`.

У цій таблиці:

- тип `NUMERIC` використано для точного зберігання ціни;
- поле `is_active` має логічний тип і показує, чи сповіщення ще активне;
- зовнішній ключ `user_id` забезпечує належність сповіщення конкретному користувачу.

#### Таблиця `public.ml_models`

Таблиця зберігає натреновані ML-моделі.

```sql
CREATE TABLE IF NOT EXISTS public.ml_models (
  id INTEGER PRIMARY KEY DEFAULT nextval('ml_models_id_seq'::regclass),
  symbol VARCHAR NOT NULL,
  interval VARCHAR NOT NULL,
  model_binary BYTEA NOT NULL,
  accuracy REAL,
  features ARRAY,
  trained_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

Цей `CREATE TABLE` створює таблицю для збереження навчених ML-моделей. У ній передбачено стовпці для криптовалюти, таймфрейму, самої моделі в бінарному вигляді, точності моделі, переліку ознак і часу навчання. Значення `id` формуються послідовністю `ml_models_id_seq`.

Тут видно:

- використання типу `BYTEA` для збереження бінарної моделі;
- поле `features ARRAY` зберігає список ознак, на яких навчалася модель;
- поле `trained_at` дає змогу визначити, коли модель була навчена і чи не застаріла вона.

#### Таблиця `public.model_predictions`

Таблиця зберігає історію прогнозів моделі.

```sql
CREATE TABLE IF NOT EXISTS public.model_predictions (
  id INTEGER PRIMARY KEY DEFAULT nextval('model_predictions_id_seq'::regclass),
  symbol VARCHAR NOT NULL,
  interval VARCHAR NOT NULL,
  signal VARCHAR NOT NULL,
  price NUMERIC NOT NULL,
  confidence NUMERIC,
  accuracy NUMERIC,
  raw_prediction VARCHAR,
  stop_loss NUMERIC,
  take_profit NUMERIC,
  created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

У цьому випадку створюється таблиця журналу прогнозів. До неї додаються поля для монети, таймфрейму, сигналу, ціни, впевненості моделі, точності, сирого прогнозу, рівнів `stop_loss` і `take_profit`, а також часу створення запису. Така структура дозволяє не лише показати прогноз користувачу, а й зберегти історію для подальшого аналізу ефективності моделі.

Саме з цією таблицею активно працює Python-код проєкту: бот читає з неї останні прогнози, а ML-модуль записує туди нові результати.

### 4.3. Де це видно в коді проєкту

У файлі `ml_engine.py` функція `save_model_to_db()` записує нові моделі в таблицю `ml_models`, а функція `log_prediction_to_db()` додає нові записи до `model_predictions`. У файлі `bot.py` функція `get_prediction_age_map()` читає історію прогнозів із `model_predictions`. Це показує, що таблиці не просто створені в SQL, а реально використовуються прикладним кодом.

У проєкті використано повну реляційну схему даних із різними типами ключів, обмеженнями цілісності та індексами. Це є прямим практичним застосуванням тем першої лабораторної роботи.

## 5. Лабораторна робота №2. Написання SQL-запитів

### 5.1. Що саме з ЛР 2 використано у проєкті

У другій лабораторній роботі вивчаються різні типи SQL-запитів. У проєкті **Crypto Pulse** SQL-запити виконуються не лише окремо в SQL-скриптах, а й безпосередньо з Python-коду через бібліотеку `psycopg2`.

У проєкті реально використовуються:

- `SELECT`;
- `INSERT`;
- `UPDATE`;
- `DELETE`;
- умови `WHERE`;
- логічні зв'язки `AND`;
- агрегатна функція `MAX`;
- групування `GROUP BY`;
- сортування `ORDER BY`;
- перевірки `IS NOT NULL`;
- пошук за шаблоном через `ILIKE`;
- обчислюване поле в результаті `SELECT`.

### 5.2. Приклад `SELECT` із групуванням у `bot.py`

У файлі `bot.py` у функції `get_prediction_age_map()` використовується запит:

```sql
SELECT
    symbol,
    interval,
    EXTRACT(EPOCH FROM (NOW() - MAX(created_at))) / 3600.0 AS age_hours
FROM model_predictions
GROUP BY symbol, interval;
```

Оператор `SELECT` вибирає з таблиці `model_predictions` символ монети, таймфрейм і додатково рахує нове поле `age_hours`. Для цього використовується агрегатна функція `MAX(created_at)`, яка знаходить найновіший прогноз у кожній групі. Вираз `NOW() - MAX(created_at)` визначає різницю між поточним часом і часом останнього прогнозу, а `GROUP BY symbol, interval` розбиває результати окремо по кожній монеті та таймфрейму.

Що робить цей код:

1. У таблиці `model_predictions` знаходить усі прогнози.
2. Для кожної пари `symbol + interval` обирає найновіший запис через `MAX(created_at)`.
3. Обчислює, скільки годин минуло від останнього прогнозу, через вираз `EXTRACT(EPOCH FROM (...)) / 3600.0`.
4. Повертає результат окремо для кожної монети та кожного таймфрейму завдяки `GROUP BY`.

Практичний сенс цього запиту такий: бот перевіряє, чи потрібно будувати новий прогноз, чи попередній ще достатньо свіжий.

### 5.3. Приклад `INSERT` у `ml_engine.py`

У функції `log_prediction_to_db()` запис нового прогнозу відбувається через:

```sql
INSERT INTO model_predictions
(symbol, interval, signal, price, confidence, accuracy, raw_prediction, stop_loss, take_profit, created_at)
VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s);
```

Оператор `INSERT INTO` додає новий рядок до таблиці `model_predictions`. Після назви таблиці перелічуються стовпці, у які буде записано дані прогнозу, а в частині `VALUES` передаються значення цих полів із Python-коду. Такий запит потрібен для фіксації кожного результату роботи ML-моделі в історії бази даних.

Цей запит додає до бази:

- монету;
- таймфрейм;
- сигнал `LONG`, `SHORT` або `NO TRADE`;
- поточну ціну;
- впевненість моделі;
- точність;
- рівні `stop_loss` і `take_profit`;
- час створення прогнозу.

Тобто кожен прогноз моделі не губиться після показу користувачу, а зберігається в історії для подальшого аналізу.

### 5.4. Приклад `DELETE` та `INSERT` для оновлення моделей у `ml_engine.py`

У функції `save_model_to_db()` спочатку виконується:

```sql
DELETE FROM ml_models
WHERE symbol = %s AND interval = %s;
```

Оператор `DELETE` видаляє старий запис із таблиці `ml_models`, але не всю таблицю, а лише ту модель, у якої збігаються `symbol` і `interval`. Тобто видаляється тільки стара модель для конкретної монети та конкретного таймфрейму.

а потім:

```sql
INSERT INTO ml_models
(symbol, interval, model_binary, accuracy, features, trained_at)
VALUES (%s, %s, %s, %s, %s, %s);
```

Після видалення старого запису оператор `INSERT INTO` додає нову модель. До таблиці записуються символ монети, таймфрейм, бінарне представлення моделі, точність, список ознак і час навчання. Разом ці два запити реалізують просту схему заміни старої моделі новою.

Пояснення логіки:

1. Для конкретної монети та таймфрейму видаляється стара модель.
2. Після цього записується нова, щойно натренована модель.
3. Так у таблиці не накопичуються зайві дублікати активних моделей, а завжди зберігається актуальна версія.

У поточній реалізації видалення старої моделі перед вставкою нової підтримується на рівні прикладного коду. Це дає змогу зберігати одну актуальну модель для потрібної монети й таймфрейму навіть без окремого унікального обмеження в самій таблиці.

### 5.5. Приклад складного `SELECT` у `ml_engine.py`

У функції `get_recent_signal_performance()` використовується:

```sql
SELECT signal, price
FROM model_predictions
WHERE UPPER(symbol) = %s
  AND interval = %s
  AND price IS NOT NULL
  AND signal IS NOT NULL
  AND signal NOT ILIKE 'NO TRADE%'
  AND created_at <= NOW() - (%s * INTERVAL '1 hour')
ORDER BY created_at DESC
LIMIT %s;
```

Цей `SELECT` вибирає лише ті прогнози, які придатні для оцінювання ефективності. Умови в `WHERE` відбирають потрібну монету, потрібний таймфрейм, відсікають порожні значення й виключають сигнали `NO TRADE`. Далі `ORDER BY created_at DESC` сортує записи від новіших до старіших, а `LIMIT` обмежує кількість рядків, щоб аналізувати тільки останню вибірку прогнозів.

Цей запит:

- обирає прогнози лише для потрібної монети;
- фільтрує їх за таймфреймом;
- відкидає порожні значення;
- не бере до аналізу сигнали типу `NO TRADE`;
- залишає лише ті прогнози, за якими вже минув потрібний горизонт часу;
- сортує записи від найновіших до старіших;
- обмежує кількість рядків через `LIMIT`.

Після виконання цього запиту Python-код перевіряє, чи справдився кожен попередній сигнал, і рахує статистику результативності.

### 5.6. Приклад `UPDATE` у SQL-схемі

У SQL-скрипті для оновлення старих записів користувачів використано:

```sql
UPDATE public.users
SET active_plan = COALESCE(active_plan, subscription, 'free'),
    subscription = COALESCE(subscription, active_plan, 'free'),
    billing_cycle = COALESCE(billing_cycle, 'monthly');
```

Оператор `UPDATE` змінює вже існуючі записи в таблиці `public.users`. Функція `COALESCE` бере перше ненульове значення, тому старі профілі користувачів отримують коректні значення тарифу й типу оплати навіть у випадку, якщо частина полів раніше була порожньою.

Цей запит приводить старі записи до єдиного формату після розширення таблиці `users`.

### 5.7. Фрагменти Python-коду, у яких база даних використовується в роботі системи

Окрім самих SQL-запитів, у проєкті є програмний код, який показує, як застосунок підключається до БД, записує результати, читає моделі та використовує дані з таблиць для прийняття рішень.

Якщо код працює як бот на сервері, параметри підключення беруться зі змінних оточення. Це дозволяє одному й тому самому коду працювати в різних середовищах без зміни логіки БД.

Додатково такий підхід не вимагає записувати логін, пароль і адресу сервера безпосередньо в коді. Конфіденційні параметри зберігаються окремо від програми, тому їх легше змінювати й безпечніше використовувати на різних середовищах розгортання.

#### Перевірка свіжості прогнозів у `bot.py`

```python
def get_prediction_age_map():
    conn = None
    try:
        conn = get_db_connection()
        cur = conn.cursor()
        cur.execute("""
            SELECT
                symbol,
                interval,
                EXTRACT(EPOCH FROM (NOW() - MAX(created_at))) / 3600.0 AS age_hours
            FROM model_predictions
            GROUP BY symbol, interval
        """)
        rows = cur.fetchall()
        cur.close()

        return {
            (str(symbol).upper(), str(interval)): float(age_hours)
            for symbol, interval, age_hours in rows
            if symbol and interval and age_hours is not None
        }
    finally:
        if conn is not None:
            conn.close()
```

Функція відкриває підключення до БД, виконує SQL-запит до таблиці `model_predictions`, отримує результати через `fetchall()` і перетворює їх на словник Python. Ключем у словнику є пара `symbol + interval`, а значенням - кількість годин від останнього прогнозу. Далі ці дані використовуються ботом, щоб не перераховувати надто свіжі прогнози повторно.

Використання блоку `finally` гарантує закриття підключення до БД навіть у разі помилки. Це важливо, оскільки незакриті з'єднання могли б накопичуватися і займати ресурси сервера бази даних.

#### Побудова списку завдань на основі даних із БД у `bot.py`

```python
def build_smart_jobs(coins):

    jobs = []
    fresh_skipped = 0

    for coin_index, coin in enumerate(coins):
        for interval_index, interval in enumerate(INTERVALS):
            age = age_map.get((coin.upper(), interval))

            if age is not None and age < PREDICTION_FRESH_HOURS:
                fresh_skipped += 1
                continue

            jobs.append({
                "coin": coin,
                "interval": interval,
                "coin_index": coin_index,
                "interval_index": interval_index,
                "age": 999999 if age is None else age,
                "missing": age is None,
            })
```

Тут уже використовується результат попереднього SQL-запиту. Функція бере інформацію про вік прогнозів із БД і формує список лише тих задач, які справді потрібно виконати. Якщо прогноз для певної монети й таймфрейму ще свіжий, він пропускається. Таким чином БД впливає не лише на зберігання інформації, а й на планування подальшої роботи бота.

Значення `missing` показує, чи відсутній прогноз у БД взагалі. Для таких випадків у полі `age` задається велике число, щоб відсутні прогнози мали найвищий пріоритет під час сортування й були побудовані першими.

Після цього `conn.commit()` фіксує зміни в базі. Саме завдяки цьому кожен згенерований сигнал зберігається для подальшої історії та аналізу.

У коді використано параметризований запит із плейсхолдерами `%s`, тому значення передаються окремо від тексту SQL. Це робить запит зручнішим і безпечнішим, ніж ручне склеювання рядка SQL. Також перед записом числові значення проходять через допоміжну функцію `safe_float()`, щоб у базу не потрапляли некоректні значення на кшталт `NaN`.

## 6. Лабораторна робота №3. Підпрограми СУБД

### 6.1. Що саме з ЛР 3 використано у проєкті

У третій лабораторній роботі вивчаються підпрограми СУБД: процедури та функції, які виконують прикладну логіку безпосередньо всередині бази даних. У проєкті **Crypto Pulse** цю роль виконують функції `PL/pgSQL`.

### 6.2. Функція `handle_new_user()`

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger
LANGUAGE plpgsql
...
```

Оператор `CREATE OR REPLACE FUNCTION` створює нову функцію або оновлює вже наявну. Функція повертає тип `trigger`, тому її можна викликати тригером після реєстрації користувача. Вказівка `LANGUAGE plpgsql` означає, що логіка функції написана мовою процедурного розширення PostgreSQL.

Призначення функції:

- створити профіль користувача в таблиці `public.users`;
- перенести до нього дані з `auth.users`;
- заповнити значення за замовчуванням, наприклад `subscription = 'free'`, `active_plan = 'free'`, `billing_cycle = 'monthly'`;
- якщо профіль уже існує, оновити його через `ON CONFLICT (id) DO UPDATE`.

Алгоритм роботи:

1. Береться новий запис із `auth.users`.
2. Із поля `raw_user_meta_data` витягуються `username`, `first_name`, `last_name`, `phone_number`, `birth_date`, `region`.
3. Створюється відповідний запис у `public.users`.
4. Якщо рядок із таким `id` уже є, виконується оновлення окремих полів.

Ця функція дозволяє не дублювати логіку створення профілю у frontend або backend-коді, а тримати її в одному місці - у самій БД.

### 6.3. Функція `check_email_exists(lookup_email text)`

```sql
CREATE OR REPLACE FUNCTION public.check_email_exists(lookup_email text)
RETURNS boolean
...
```

Тут створюється функція з одним вхідним параметром `lookup_email` типу `text`. Оскільки вона повертає `boolean`, результатом виклику є лише два можливі значення: `true` або `false`.

Призначення функції:

- перевірити, чи є вже в системі користувач із заданим email;
- повертати лише `true` або `false`.

Усередині використано:

```sql
RETURN EXISTS (
  SELECT 1
  FROM auth.users
  WHERE lower(email) = lower(lookup_email)
);
```

Конструкція `RETURN EXISTS` не повертає весь знайдений рядок, а лише перевіряє, чи існує хоча б один відповідний запис. Вираз `lower(email) = lower(lookup_email)` приводить обидва значення до нижнього регістру, щоб перевірка працювала однаково для різних варіантів написання email.

Пояснення:

- `EXISTS` перевіряє сам факт наявності рядка;
- `lower()` робить перевірку нечутливою до регістру, тому `User@mail.com` і `user@mail.com` вважаються однаковими.

### 6.4. Функція `delete_current_user()`

```sql
CREATE OR REPLACE FUNCTION public.delete_current_user()
RETURNS void
...
```

У цьому випадку створюється функція, яка нічого не повертає назовні, тому вказано тип `void`. Її завдання не у видачі значення, а у виконанні дії - видаленні поточного користувача.

Призначення функції:

- видалити саме поточного авторизованого користувача;
- не дати користувачу передати чужий `id` вручну.

У функції використовується:

```sql
current_user_id := auth.uid();
```

Цей рядок присвоює змінній `current_user_id` id того користувача, який зараз авторизований у системі. Завдяки цьому функція працює саме з поточним користувачем, а не з довільним id, переданим вручну.

Після цього видаляється рядок із `auth.users`. Завдяки `ON DELETE CASCADE` автоматично очищуються пов'язані записи в `public.users`, `user_favorites` та `alerts`.

### 6.5. Де це видно в проєкті

Ці функції розміщені в SQL-частині проєкту й відповідають за логіку користувачів. Python-код окремо не дублює цю логіку: він працює з уже готовими даними, а створення профілю, перевірка email і видалення акаунта винесені на рівень СУБД.

### 6.6. Висновок по ЛР 3

У проєкті функції СУБД використовуються для автоматизації повторюваних дій і забезпечення єдиного способу обробки даних користувача. Це є прямим практичним застосуванням теми підпрограм СУБД.

## 7. Лабораторна робота №4. Тригери

### 7.1. Що саме з ЛР 4 використано у проєкті

У четвертій лабораторній роботі вивчаються тригери - механізми, які автоматично запускаються при певних подіях у базі даних. У проєкті **Crypto Pulse** використано тригер, який автоматизує створення профілю користувача.

### 7.2. Тригер `on_auth_user_created`

```sql
CREATE TRIGGER on_auth_user_created
AFTER INSERT ON auth.users
FOR EACH ROW
EXECUTE FUNCTION public.handle_new_user();
```

Оператор `CREATE TRIGGER` створює тригер із назвою `on_auth_user_created`. Він пов'язується з таблицею `auth.users` і запускається після кожної вставки нового рядка. Після цього автоматично виконується функція `handle_new_user()`, яка створює профіль у прикладній таблиці користувачів.

Що означає цей код:

- `AFTER INSERT` - тригер запускається після створення нового користувача;
- `ON auth.users` - подія відстежується в системній таблиці Supabase Auth;
- `FOR EACH ROW` - тригер спрацьовує для кожного нового користувача окремо;
- `EXECUTE FUNCTION public.handle_new_user()` - після спрацювання виконується функція, яка створює профіль у `public.users`.

### 7.3. Як це працює в проєкті

Послідовність подій така:

1. Користувач реєструється в застосунку.
2. Supabase створює новий рядок у `auth.users`.
3. Тригер `on_auth_user_created` спрацьовує автоматично.
4. Викликається функція `handle_new_user()`.
5. У `public.users` створюється профіль із потрібними полями.

Таким чином, backend або frontend не повинні окремо пам'ятати про створення профілю. База даних сама підтримує необхідну цілісність між системною та прикладною таблицею користувачів.

### 7.4. Висновок по ЛР 4

У проєкті тригер застосовано для автоматизації бізнес-процесу реєстрації. Це хороший приклад того, як механізм тригерів використовується не окремо "для галочки", а для реальної логіки застосунку.

## 8. Лабораторна робота №5. Адміністрування БД

### 8.1. Що саме з ЛР 5 використано у проєкті

У п'ятій лабораторній роботі розглядаються користувачі, ролі та привілеї. У проєкті **Crypto Pulse** ці поняття реалізовані через механізми PostgreSQL і Supabase:

- ролі `authenticated` і `anon`;
- надання прав через `GRANT`;
- захист таблиць через `Row-Level Security`;
- окремі політики доступу для `SELECT`, `INSERT`, `UPDATE`, `DELETE`.

### 8.2. Приклади надання прав

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON public.user_favorites TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.alerts TO authenticated;
GRANT SELECT, INSERT, UPDATE ON public.users TO authenticated;
GRANT EXECUTE ON FUNCTION public.check_email_exists(text) TO anon, authenticated;
GRANT EXECUTE ON FUNCTION public.delete_current_user() TO authenticated;
```

Оператор `GRANT` надає права ролям бази даних. У цьому прикладі роль `authenticated` отримує дозвіл читати, додавати, змінювати та видаляти записи в потрібних таблицях, а ролі `anon` і `authenticated` отримують дозвіл викликати окремі функції. Таким чином визначається, які дії взагалі доступні різним типам користувачів системи.

Пояснення:

- авторизовані користувачі можуть працювати з власними обраними монетами та сповіщеннями;
- авторизовані користувачі можуть читати й редагувати свій профіль;
- анонімному користувачу дозволено лише викликати перевірку email перед реєстрацією;
- видалення акаунта дозволене лише авторизованому користувачу.

### 8.3. Row-Level Security для таблиці `user_favorites`

```sql
ALTER TABLE public.user_favorites ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can read own favorites"
ON public.user_favorites
FOR SELECT
TO authenticated
USING (auth.uid() = user_id);
```

Перший рядок через `ALTER TABLE` вмикає механізм Row-Level Security для таблиці `user_favorites`. Далі `CREATE POLICY` створює конкретне правило читання: авторизований користувач може бачити лише ті рядки, де значення `user_id` збігається з його власним ідентифікатором `auth.uid()`.

Пояснення:

- `GRANT` сам по собі дає право працювати з таблицею;
- `RLS` уточнює, з якими саме рядками користувач може працювати;
- умова `auth.uid() = user_id` означає, що користувач бачить лише власні рядки.

Для цієї ж таблиці створені окремі політики для:

- читання;
- вставки;
- оновлення;
- видалення.

### 8.4. Row-Level Security для таблиці `alerts`

Для `alerts` використовується така сама логіка:

```sql
CREATE POLICY "Users can read own alerts"
ON public.alerts
FOR SELECT
TO authenticated
USING (auth.uid() = user_id);
```

Тут створюється окрема політика безпеки для таблиці `alerts`. Вона працює за тим самим принципом, що й для обраних монет: кожен користувач має доступ лише до власних сповіщень.

Це важливо, тому що сповіщення користувача є персональними налаштуваннями й не повинні бути доступні іншим користувачам.

### 8.5. Row-Level Security для таблиці `users`

```sql
CREATE POLICY "Users can read own profile"
ON public.users
FOR SELECT
TO authenticated
USING (auth.uid() = id);
```

У таблиці `users` політика порівнює `auth.uid()` вже не з полем `user_id`, а з полем `id`, тому що саме `id` є ключем профілю. Отже, авторизований користувач може прочитати лише той профіль, який належить йому самому.

Тут `auth.uid()` порівнюється вже не з `user_id`, а з `id`, бо в таблиці `users` сам `id` і є ідентифікатором профілю.

### 8.6. Де це видно в логіці проєкту

SQL-рівень доступу пов'язаний із тим, як проєкт працює з персональними даними:

- `user_favorites` містить персональний список монет;
- `alerts` містить приватні сповіщення користувача;
- `users` містить персональні дані профілю.

Тому в БД встановлено не лише загальні права на таблиці, а й окремі правила, які не дозволяють користувачу читати або змінювати чужі записи.

### 8.7. Заплановані рівні підписки та обмеження доступу

У проєкті вже передбачені поля, пов'язані з підпискою користувача:

```sql
subscription VARCHAR(20) DEFAULT 'free',
active_plan VARCHAR(20) DEFAULT 'free',
billing_cycle VARCHAR(10) DEFAULT 'monthly'
```

Ці поля зберігаються в таблиці `public.users` і вже зараз дають основу для поділу користувачів за рівнями доступу. Поле `subscription` може описувати загальний тип підписки, `active_plan` - фактично активний тариф, а `billing_cycle` - спосіб оплати, наприклад щомісячний або річний.

Надалі на сайті планується реалізувати кілька рівнів підписки, наприклад:

1. `free` - базовий тариф;
2. `pro` - розширений тариф;
3. `premium` - повний доступ до всіх можливостей.

Можлива логіка обмежень:

| Рівень підписки | Можливості |
|---|---|
| `free` | Обмежена кількість обраних монет, невелика кількість alerts, базові прогнози |
| `pro` | Більше обраних монет, більше alerts, доступ до розширеної статистики та частіших оновлень |
| `premium` | Максимальні ліміти, повний доступ до аналітики, усі таймфрейми та пріоритетні функції |

Таку систему планується реалізувати у два рівні:

1. **На рівні бази даних** - зберігати активний план користувача в `public.users`, а при потребі додати окрему таблицю, наприклад `subscription_plans`, де будуть описані ліміти кожного тарифу: максимальна кількість `favorites`, максимальна кількість `alerts`, доступні таймфрейми, частота оновлення прогнозів.
2. **На рівні логіки застосунку** - перед виконанням дії перевіряти `active_plan` користувача та порівнювати його з дозволеними лімітами. Наприклад, якщо користувач тарифу `free` уже має максимальну кількість alerts, застосунок не дозволить створити ще одне сповіщення.

У майбутньому можлива структура таблиці тарифів:

```sql
CREATE TABLE public.subscription_plans (
  code VARCHAR(20) PRIMARY KEY,
  max_favorites INTEGER NOT NULL,
  max_alerts INTEGER NOT NULL,
  allow_advanced_analytics BOOLEAN NOT NULL DEFAULT false,
  allow_all_timeframes BOOLEAN NOT NULL DEFAULT false
);
```

Оператор `CREATE TABLE` у цьому прикладі створює довідник тарифних планів. Поле `code` містить назву тарифу, а інші стовпці задають конкретні ліміти та можливості кожного плану. Такий підхід зручний тим, що правила тарифів не потрібно жорстко прописувати в коді застосунку - їх можна змінювати без зміни основної структури користувачів.

Наприклад, для перевірки кількості alerts можна буде використовувати такий принцип:

```sql
SELECT COUNT(*)
FROM public.alerts
WHERE user_id = auth.uid();
```

Цей запит рахує, скільки сповіщень уже створив поточний користувач. Після цього кількість можна порівняти з лімітом його тарифу і дозволити або заборонити створення нового alert.

Тобто надалі рівні підписки будуть використовуватися не лише як інформаційне поле в профілі, а як основа для реального розмежування функціональності сайту.

### 8.8. Висновок по ЛР 5

У проєкті адміністрування БД реалізоване через ролі, привілеї та політики безпеки. Особливо важливим є використання `Row-Level Security`, оскільки воно забезпечує не просто доступ до таблиці, а точний контроль доступу до конкретних рядків.

## 9. Загальний висновок

У проєкті **Crypto Pulse** реально використовуються основні теми лабораторних робіт з баз даних:

- побудова схеми реляційної БД;
- ключі, зв'язки та обмеження цілісності;
- SQL-запити різних типів;
- функції СУБД;
- тригери;
- ролі, привілеї та політики доступу.

База даних у проєкті не є окремим формальним елементом, а безпосередньо бере участь у роботі застосунку: зберігає користувачів, сповіщення, обрані монети, ML-моделі та результати прогнозів.
